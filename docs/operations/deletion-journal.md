# 删除意图日志：部署与恢复操作

`DeletionJournal` 是与数据库、`APP_FILES_ROOT` 分开的追加文件。构造器必须收到运维显式配置的**绝对持久目录**，没有回退路径。目录应由运维创建、限制为服务账号读写，并与主数据库快照分别备份；不应把它放进随数据库一同回滚的卷。首次新部署须一次性调用 `DeletionJournal.initialize(root)`，它接受全新目录或空目录并写入 `deletions.tsv` 和 `head.tsv`；已有完整日志只做校验，缺任一文件或准备初始化的目录混有未知文件时拒绝初始化。常规启动及备份恢复只调用 `new DeletionJournal(root)`，目录或任一文件缺失均拒绝启动。初始化入口绝不能作为恢复时的自动回退。日志只含单调序号、账号 ID、来源 UUID、删除时间、前一哈希及本行哈希；不写标题、origin ID、正文或引用原文。

每次 `append(accountId, sourceId, deletedAt)` 在进程内互斥及 OS 文件锁下先完整复核旧链和 `head.tsv`，再追加并 `force` 日志文件，原子替换且 `force` 链头文件，最后 `force` 目录。调用方必须在数据库删除/撤权事务**提交前**完成此调用；若数据库回滚，可保留多余意图，恢复时再次撤权是幂等的。日志写入失败、校验失败或链头不匹配时，调用方应停止删除提交并阻止恢复库开放读取。文件锁允许同一持久目录上多个进程顺序追加，但该目录必须位于支持可靠文件锁、原子同目录 rename 和 fsync 的本地文件系统；不能直接换成未经验证的网络卷。

`readAll()` 在同一锁下校验每一行序号、规范字段、SHA-256 链、完整行结束符和独立链头，返回不可变顺序列表。整行尾截断由 `head.tsv` 检出；半行截断由换行检查检出；内容篡改由哈希链检出。若日志行已 `force` 但链头更新前崩溃，或原子替换失败，链头会落后，常规构造器及读取均拒绝继续；这可能使恢复实例暂时无法开放读取，但不会把未记录的删除静默遗漏。离线核验完整末行及外部水位后，可由运维决定将链头前移，保留可能多出的删除意图；不能静默截短日志或自动前移链头。两个文件一起被恶意回滚不能仅靠本地哈希发现；生产恢复应把链头序号和哈希作为独立备份清单/外部水位校验。哈希链只提供损坏检出，不提供身份签名。

恢复操作顺序：隔离恢复实例和 worker，挂载**未回滚的独立日志**，核对外部备份清单水位，以 `APP_AGENT_RETENTION_INITIALIZE_JOURNAL=false` 启动。实际 `SourceDeletionService.recoverBeforeServing` 在 Flyway 后、HTTP/worker 生命周期开放前验证全链，并分别核对 `ma_deletion_replay` 回放水位和 `ma_source_deletion` 最高已提交序号所对应的哈希，按 `(accountId, sourceId)` 幂等撤销全部版本，提交 `ma_deletion_replay` 水位。不存在于旧备份的来源仍创建最小删除墓碑。所有模式都要求该日志，包括回退 LEGACY；损坏、缺失或日志落后于库水位时启动失败。源立即不可读/索引；剩余数据库原文和原图在显式启用的清理调度中继续清除。文件引用身份和请求/结果行保留为墓碑，不能级联删除独立发布答复。

正常 `withdraw` 在同一业务事务内保存删除墓碑，因此最高已提交删除序号也参与恢复校验，不能只依赖上次启动的回放水位。取最大日志序号，不依赖跨账号事务的提交先后；任一记录水位超出日志长度或对应哈希不一致时，在重放前失败。日志条目多于数据库记录是允许的：数据库事务回滚后，已落盘的删除意图仍须重放。正常入口按账号串行，且仅接受 ACTIVE 来源；同一来源在事务回滚后重试时，成功事务保存其自己的序号。恢复校验没有给正常删除增加全局锁，不改变现有锁顺序。

本地数据库仍保留较新删除墓碑或回放水位时，可发现日志与链头整对回退；若**数据库、日志和链头一起整体回滚**，本地记录无法证明丢失的后缀，仍须外部水位或独立备份清单。此修复是启动恢复检查，不是运行期间卷被替换的持续监测。

目标文件系统需分别验证双进程追加、断电恢复与备份水位校验，并记录数据量、耗时和恢复结果。
